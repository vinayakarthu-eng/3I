## Read this first: the codebase as it exists today

**Environment**
- Node 20 via nvm (`~/.nvm`), npm workspaces + Turborepo. Docker Desktop runs Postgres 16 + Redis
  (`docker compose up -d`). If `docker` isn't on PATH, it lives at `~/.docker/bin/docker`.
- `.npmrc` sets `legacy-peer-deps=true` — keep it (drizzle-orm's optional peers otherwise break hoisting).
- shadcn/ui must be added with the pinned CLI: `cd apps/web && npx shadcn@2.1.8 add -y -o <component>`.
  After adding, delete `apps/web/node_modules` and `apps/web/package-lock.json` and run `npm install` from
  the root, and make sure `tailwind-merge` stays on `^2.x` (v3 is Tailwind-v4-only). Newer shadcn CLIs
  generate Tailwind v4/oklch output that breaks this Tailwind v3 setup.
- Don't run `next build` while `next dev` is running — they share `apps/web/.next`. Stop dev first, or
  `rm -rf apps/web/.next` before restarting dev.

**Layout**
| Workspace | Notes |
| --- | --- |
| `apps/web` | Next.js 14 App Router, Tailwind v3, shadcn/ui (new-york, zinc, HSL CSS vars), Recharts 2, next-themes. Data access = **server actions** (no tRPC) + server components querying `@drillforce/db` directly. |
| `apps/slack-bot` | Bolt socket-mode IC bot. Exits cleanly when Slack tokens are missing. `npm run simulate -w @drillforce/slack-bot -- <drill-id>` runs a drill without Slack. |
| `workers/scoring-engine` | Polls drills in `scoring`, auto-scores, writes `drill_composite`, moves to `debriefing`. Exports `autoScoreDrill`, `recordManualScores`, `finalizeIfComplete`. Has `node:test` tests (`npm test`). |
| `workers/report-generator` | Polls drills in `debriefing`, writes AARs to `drill_reports` (Claude Opus 5.5 with structured outputs, or a template when no `ANTHROPIC_API_KEY`). |
| `packages/db` | Drizzle schema in `src/schema.ts`, migrations in `drizzle/`, `seed.ts` (truncates and reloads everything). Scripts: `npm run db:generate`, `npm run db:migrate`, `npm run db:seed` (run from the repo root). |
| `packages/shared` | Enums/labels, `DRILL_TEMPLATES` (5 templates in `src/templates.ts`), status-transition and action-workflow helpers. |

**Patterns to follow**
- Server actions return `ActionResult<T>` (`{ ok: true, data } | { ok: false, error, fieldErrors? }`) from
  `apps/web/src/app/drills/actions.ts`; client components call them via `useAction()` (`src/hooks/use-action.ts`),
  which toasts errors. Validate with zod; scope every query to the current org.
- Current user = `getCurrentUser()` in `src/lib/current-user.ts` (first seeded admin; no auth yet).
- Reads live in `src/lib/queries.ts` (`server-only`). Text "enums" are `text` columns with CHECK constraints
  generated by the `oneOf()` helper in the schema — add new enums the same way.
- Chart colors use `hsl(var(--chart-N))` / `hsl(var(--border))` etc. so they work in light and dark mode.
- Status transitions: `allowedTransitions()` in `packages/shared`. Status changes are logged as
  `drill_events` of type `system` with `payload.kind = "status_change"` (the Overview timeline reads these).
- Existing routes that must keep working: `/`, `/drills`, `/drills/new`, `/drills/[id]` (tabs, `?tab=`),
  `/drills/[id]/edit`, `/drills/[id]/aar`, `/actions`, `/reports`, `/templates`, `/settings`.
- Verify UI changes in a browser, not just with the build.

## PHASE 1: Simulated Monitoring Dashboard

UptimeLabs' killer feature is a browser-based simulated monitoring environment that looks like real Datadog/Grafana. Teams see graphs, logs, and alerts during a drill — no real infrastructure needed.

### Build: /drills/[id]/simulate

Create a full-screen simulation view that participants see during an active drill. This is the drill "war room."

**Simulated Monitoring Panel (left 60% of screen)**
Build a realistic monitoring dashboard using recharts:

- **Service Health Grid**: 6 service tiles (API Gateway, Database Primary, Database Replica, Cache Layer, Message Queue, CDN) each showing status (healthy/degraded/down) with colored indicators
- **Metrics Charts** (live-updating):
  - Requests per minute (line chart, updates every 2 seconds with synthetic data)
  - Error rate % (line chart, spikes when inject happens)
  - P99 latency ms (line chart)
  - CPU utilization % (area chart)
- **Log Stream**: scrolling log viewer showing synthetic log lines (mix of INFO, WARN, ERROR) — styled like a real terminal. Logs should include realistic timestamps, service names, and messages. When a drill inject happens, ERROR logs should spike.
- **Alert Banner**: when the drill scenario triggers, show a red alert bar: "🚨 ALERT: [scenario description] — Severity: SEV-1"

**Communication Panel (right 40% of screen)**
- Chat interface styled like Slack
- Shows drill channel messages
- Participants can type messages (stored as drill_events)
- IC bot messages appear here
- Inject messages appear with ⚠️ icon
- Timestamp on every message

**Simulation Engine (packages/shared/src/simulation-engine.ts)**
- Function `generateMetrics(scenario, elapsedMinutes, injects)` that produces realistic metric data
- Normal state: metrics hover around healthy baselines with small random variation
- When an inject fires: error rate spikes, latency increases, request rate may drop — the shape depends on scenario type
- Pre-built metric profiles for scenario types:
  - `database_failover`: latency spikes to 5000ms, error rate jumps to 40%, connection pool exhaustion in logs
  - `dns_outage`: requests drop to near-zero, all services show "connection timeout" errors
  - `credential_leak`: normal metrics but security log entries about unauthorized access
  - `high_traffic`: request rate 10x spike, latency gradual increase, queue depth growing
  - `deployment_failure`: error rate 100% for one service, cascading errors to dependents

**Log Generator (packages/shared/src/log-generator.ts)**
- Function `generateLogs(scenario, elapsedSeconds, injects)` returning log lines
- Each log: `{timestamp, level, service, message}`
- Normal state: 80% INFO, 15% WARN, 5% ERROR
- During incident: flip to 20% INFO, 30% WARN, 50% ERROR with scenario-specific messages
- Realistic service names and log messages (not generic placeholder text)

**Data flow**
- Simulation runs client-side using setInterval (no server needed for metrics generation)
- Drill injects trigger metric/log profile changes
- Chat messages go through server actions to drill_events table
- When drill status is 'active', this page auto-refreshes participant list

### New Database Table

```
drill_injects: id, drill_id, description, trigger_at_minutes (int), inject_type (metric_spike/log_flood/alert/comms), payload (jsonb), fired (boolean default false), fired_at (timestamptz)
```

### Seed Data
Add 5-8 pre-timed injects to each drill template's scenario config. Example for database failover:
- t+0: "Database primary reporting high replication lag"
- t+3: "Connection pool exhaustion — new connections timing out"
- t+5: "Application error rate exceeding 40%"
- t+8: "Customer support: 200+ tickets in last 5 minutes"
- t+12: "CEO Slack message: Board meeting in 1 hour, need status update"

### Link from Drill Detail
- When drill status is 'active', show "Enter Simulation" button on drill detail page
- Button links to /drills/[id]/simulate
